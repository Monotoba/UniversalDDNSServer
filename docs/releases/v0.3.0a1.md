# UniversalDDNSServer v0.3.0a1 — Alpha release candidate

**Status:** Prepared release candidate, not tagged or published. Owner approval is required before publication. Intended only for experimental, isolated loopback-only deployments.

## Changes since v0.2.0a1

- Experimental DynDNS2-compatible `GET /nic/update` endpoint for one authorized, server-configured A/AAAA hostname and explicit address, using HTTP Basic with a server-issued API token as the password.
- `nochg <ip>` after authorized authoritative DNS observation confirms an existing match; `good <ip>` only after the independent worker records successful DNS publication.
- Bounded wait for worker completion (five seconds by default); pending, uncertain or failed publication returns `911` rather than false success. Unsupported client options, unmapped hosts, invalid IPs, and credentials are rejected.
- New optional `UniversalDDNSDynDNS2` adapter in Monotoba/UDDNSUpdater, alongside the existing, intent-aware REST adapter; cross-repository integration exercises actual loopback HTTP, a separate publishing worker and isolated BIND 9.
- Local upgrade, client configuration and troubleshooting guide; additive rollout with existing REST v1 endpoints, SQLite credentials and intent journal preserved. No new server configuration keys or schema migration for this feature.

## Deployment and compatibility

- Python 3.11+; tested by CI with Python 3.11–3.13 and isolated BIND 9.
- Existing REST v1 and CLI token administration remain supported.
- The DynDNS2 compatibility subset requires a configured hostname and an explicit `myip` parameter; the server does not infer the client's source address. Only a single configured, authorized host mapping is supported.
- See [DynDNS2 behavior](../dev/DYNDNS2_COMPATIBILITY.md) and [experimental v0.3 upgrade guide](../operations/V0_3_LOCAL_UPGRADE.md).
- `UniversalDDNSDynDNS2` is restricted to local loopback use. The original UDDNSUpdater REST adapter remains preferable for durable intent tracking.

## Important limitations

- This is not full DynDNS2 support: router-specific options, multiple hostnames, generic protocol variants and source-IP inference are not implemented.
- A `911` response means the update is not confirmed; the client must not blindly retry an ambiguous publication. `good` records worker completion, not worldwide DNS propagation.
- Not for public internet exposure: no production TLS ingress, distributed throttling, high availability, or bundled authoritative DNS server.
- Basic authentication must remain exclusively on the loopback deployment; credentials must not traverse unencrypted networks.
- Reconciliation, backoff, updater rollback, and crash recovery are deliberately bounded and do not provide exactly-once or production disaster-recovery guarantees.
- Existing experimental VM has **not** been upgraded to this candidate; automated preservation and real-BIND CI do not constitute a live-host migration certification.
