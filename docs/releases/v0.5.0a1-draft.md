# v0.5.0a1 — draft experimental alpha release notes

**Status: release candidate under review. Not tagged, published, approved for installation, or deployed.**

UniversalDDNSServer v0.5.0a1 is an experimental milestone built around a **local-only, read-only** browser management dashboard. It is not a production-ready, publicly exposed DDNS management system.

## What's new
- Local dashboard at `http://127.0.0.1:8765/dashboard` on the machine running the experimental loopback API; dashboard resources reject non-loopback clients.
- Bearer-authenticated, record-scoped discovery, individual record details and known-intent inspection using existing `intents:read` permission.
- Bounded recent-intent history with principal ownership and current-record filtering, optional record/status filters, and status summaries only for returned results.
- Read-only authoritative DNS observation via the configured RFC 2136 backend: `matches_template`, `differs_from_template`, `absent` and `unavailable`. A timeout, bad response, or network failure is **unavailable**, not proof of absence; comparison to a template does not verify a particular intent.
- Additional isolated SCM_RIGHTS Linux robustness coverage, including error propagation, kernel descriptor exhaustion and recovery.
- Updated SPDX BSD-2-Clause package license metadata and release candidate documentation.

## Existing core functionality
- Experimental A/AAAA record catalog, scoped HTTP update intake and durable SQLite intents.
- RFC 2136/TSIG BIND 9 publication through a separately supervised worker.
- DynDNS2-compatible endpoint for statically configured records, with UDDNSUpdater interoperability.
- Local operator CLI record and credential administration and audit.

## Limitations and security scope
- **Local-only.** Do not expose the API or dashboard to the internet or route it through an untrusted reverse proxy.
- Browser interface cannot modify records, issue/revoke tokens, or administer users. No remote administration API or delegated RBAC.
- Dashboard credentials are held only in the page's password field; use a trusted local browser and clear the field after use.
- A queued `pending` intent does not mean published DNS. Ambiguous external updates require observation and controlled recovery.
- Process-local rate limiting, SQLite operator write access, API runtime TSIG credential handling, and cross-process/multi-writer assurances need further security work.
- Full v0.5 dashboard functionality has **not** yet been verified in the user's Ubuntu VM; prior v0.4 VM and backup evidence must not be reattributed to this candidate.
- Production HTTPS, global rate limiting, distributed operations and verified production disaster recovery are not supplied.
